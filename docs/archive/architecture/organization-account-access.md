# Account Organization Access — Source Contract

## Scope

One authenticated AccountID resolves to one Person through `accounts.person_id`.
That Person can hold active `organization_members` in multiple Organizations.
This change does **not** create new RBAC tables, project scopes or account-wide
roles. The only persisted membership roles remain `owner` and `member`.

## HTTP contract

All three reads use the existing authentication and VerifiedContact middleware.

| Operation | Returned data | Authorization |
| --- | --- | --- |
| GET /organizations | Array of organizations, current membership and effective capabilities; `[]` when none | Account's active memberships |
| GET /organizations/{id} | One organization, current membership and effective capabilities | Active member only; 404 if absent/not a member |
| GET /organizations/{id}/members | Array of active members with person ID, role and join time, without phone/email | Active owner only; 404 if absent/not an owner |
| PATCH /organizations/{id} | Updated organization | Existing SQL owner predicate |
| POST /organizations/{id}/members | New member | Existing SQL owner predicate |

Sample element from GET /organizations:

```json
{
  "party_id": 101,
  "name": "Example Company",
  "created_at": "2026-10-01T08:00:00Z",
  "membership": {
    "id": 15,
    "role": "owner",
    "joined_at": "2026-10-01T08:00:00Z"
  },
  "permissions": [
    "organization.view",
    "organization.update",
    "organization.members.view",
    "organization.members.add"
  ]
}
```

## Capability contract

- Owner: `organization.view`, `organization.update`,
  `organization.members.view`, `organization.members.add`.
- Member: `organization.view`.
- Not a member or ended membership: no organization visibility and no capabilities.

Returned permission strings are constructed in `internal/api/handler/resources.go` only, **a read projection for the client**, not an
authorization credential or a grant that survives role revocation. Backend
operations consult current membership and role in PostgreSQL each time.
Only existing implemented operations are advertised. A JWT's AccountID alone
never confers Organization access.

The existing `owner`/ `member` predicates in SQL are the operation authority. The service carries membership facts without assembling HTTP permissions;
do not add a second middleware permissions registry. Expansion to custom
roles/permissions requires an explicit migration of both enforcement and
projection in the same change, not two competing grants.

## Data and tests

Queries are authored only in `db/query/organization.sql` and generated by
SQLC v1.30.0. The separate table rename in migration 000011 preserves active-member and owner predicates.
Tests cover two organizations owned by one Account, a member of exactly one
organization, an outsider, read permissions, denied member-management,
privacy of member lists, and immediate loss of read access after membership
ends. The production external provider tests are outside this change.
